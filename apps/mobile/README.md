# TrendLIX People — the employee mobile app: plan and development guide

This file is the working guide for building the employee app. Read it before every session of work on the app, keep
the **Status** section at the bottom up to date at the end of each phase, and record every decision the owner makes
here (with the date and their words) before building on it.

---

## 1. What the owner asked for (20 October 2026)

- "what if we tried to build a mobile app for the employees? to enable them to check in and out, and apply for their
  requests" — then, from Claude's options:
  - **A store app** (App Store and Google Play, later) wrapping the web system — not a separate native rebuild.
  - **First version:** Check in / Check out · Requests (leave, permission, reimbursement with a receipt photo,
    attendance corrections, raise requests) · My attendance and payslips · managers and team leads approve from the
    phone.
  - **Push notifications:** yes (decisions, things waiting for someone, a check-in reminder).
  - **Sign-in:** Face ID / fingerprint after the first password sign-in.
- "we will not test the first version of the app on google play or on app store but we will deploy apps on github and
  use github action with yml ci cd file; actions will be responsible for build the app so that i can download the apk
  app to test it while developing process phases."
  - So: **no store submission in the first version.** Every phase ends with an **APK built by GitHub Actions** that
    the owner downloads from the workflow run (or a GitHub Release) and installs on an Android phone.
  - iPhone: an unsigned build can't be installed on a phone without an Apple Developer account, so iOS comes after the
    Android phases (see Phase 6).
- Language of the code: TypeScript everywhere we write (pages and server); the iOS (Swift) and Android (Kotlin/Java)
  shells are generated by Capacitor with small settings only. The app's interface is English; Arabic was offered
  (2–3 days, RTL) and not decided yet — build every string so it can be translated later (no text in native code).

## 2. The shape of it (architecture)

```
 Android / iOS phone
 ┌───────────────────────────────────────────────┐
 │  TrendLIX People (Capacitor shell, apps/mobile) │
 │  ├─ WebView → https://people.trendlix.com/app   │  the phone pages (apps/web, Next.js, /app routes)
 │  └─ native plugins: location, push, biometrics, │  reached from the pages through window.Capacitor
 │     camera, secure storage, network status      │
 └───────────────────────────────────────────────┘
                  │ HTTPS (the website only)
                  ▼
   Vercel: apps/web (Next.js) ── server-side ──► API (NestJS, VPS, private CA) ──► PostgreSQL
```

- **Why the app loads the website's pages:** the system's pages are server-rendered (server components, server
  actions) and the API is reachable **only from the website** (private CA — see DEPLOY.md and the job-offers memory).
  So the app never calls the API directly: it shows `people.trendlix.com/app/...`, and the website talks to the API as
  it does today. Every rule (approvals, C-level hiding, limits, grace, payroll filling) stays in one place.
- **The phone pages (`/app`)** are a separate, phone-first area of the web app with its own layout (bottom tab bar, big
  touch targets, one hand), reusing the existing data loaders, server actions and shared rules. They also work in a
  phone's browser, so each phase can be tried before the APK exists.
- **The native bridge:** pages call native features only through one helper, `apps/web/src/lib/native.ts`, which
  feature-detects `window.Capacitor` (present only inside the app) and falls back to the browser's own APIs
  (navigator.geolocation, file input with `capture`) when it isn't. The web app does **not** depend on Capacitor npm
  packages; it uses the injected `window.Capacitor.Plugins` with typed wrappers.
- **The shell (`apps/mobile`):** a Capacitor project (`capacitor.config.ts` with `server.url` =
  `https://people.trendlix.com/app`, `allowNavigation` for the domain), the Android project (`android/`), later the iOS
  project (`ios/`), plugins, app icon and splash from the company logo, permission texts, and an offline screen bundled
  in `www/` (shown when the site can't be reached).
- **Signing in on the phone:**
  1. The first time: the normal sign-in page (work email + password) inside the app → a normal web session cookie.
  2. The app then offers "Use Face ID / fingerprint next time": the website asks the API for a **device credential**
     (a random secret, stored hashed in the database per user and device, long-lived, revocable); the app keeps it in
     the phone's secure storage (Keychain / Android Keystore) behind the biometric prompt.
  3. Next opens: biometric prompt → the app sends the device credential to the website → the website asks the API for a
     fresh session and sets the cookie → the app opens Home. A revoked or expired credential falls back to the password.
  4. The user's devices are listed on their profile (and for HR/Admin) with "Sign out this device" (revoke).
- **Push notifications:** Firebase Cloud Messaging (FCM, HTTP v1) for Android now (and iOS through APNs later). The app
  registers its push token with the website → API (`push_devices`). The API sends through a small FCM client written
  with Node's own crypto + fetch (no new dependency), **switched off until the owner creates the Firebase project** and
  the service-account key is set on the server (`FCM_PROJECT_ID`, `FCM_CLIENT_EMAIL`, `FCM_PRIVATE_KEY` in
  deploy/.env — never asked for in chat). An in-app **inbox** (bell) holds the same notifications, so nothing is lost
  while push is off.
- **Location:** check-in already classifies office / remote / unknown on the server from the coordinates sent and keeps
  no coordinates (see packages/shared check-in.ts). In the app, the native location plugin gives better accuracy, and on
  Android it reports **mock (fake GPS) locations** — sent as `mock: true` and flagged on the day like a check-in from
  the wrong place.

## 3. Phases (each ends with a downloadable APK and a short note to the owner)

Every phase: build → all checks (API unit, the whole e2e suite, tsc, lint; web typegen, tsc, eslint, vitest, build;
the mobile workflow green) → commit and push to main (auto-push rule) → the web deploy (Vercel) and backend deploy
(GitHub Actions) as today → the **Android APK** from the mobile workflow → tell the owner where to download it and what
to try.

### Phase 0 — Scaffolding and CI (the APK pipeline)
- `apps/mobile`: package.json (`@trendlix/mobile`), Capacitor core + CLI + Android platform, `capacitor.config.ts`,
  `www/` with the offline page and a tiny loader, `android/` generated by `npx cap add android` and committed.
- App id `com.trendlix.people`, name **TrendLIX People** (owner may rename), version from the workflow run number.
- `.github/workflows/mobile-android.yml`:
  - on: push to main touching `apps/mobile/**` (and the workflow file), plus `workflow_dispatch` (run by hand), plus
    tags `mobile-v*` (also attaches the APK to a GitHub Release).
  - ubuntu-latest, Node 22 (the repo's engines), Java 21 (Temurin), Android SDK via the runner's preinstalled SDK.
  - `npm ci` → `npx cap sync android` → `./gradlew assembleDebug` (Phase 0–5: debug-signed APK, installable directly)
    → upload `app-debug.apk`, renamed `trendlix-people-<version>.apk`, as an artifact named
    `trendlix-people-<version>`, kept 30 days.
  - Later (before any store): a release build signed with a keystore kept in GitHub Secrets.
- How the owner installs it: Actions → the latest "Mobile (Android)" run → Artifacts → download → unzip → open the APK
  on the phone (allow "install unknown apps" once). The README's section 6 says this in plain words.
- Done when: a push builds an APK that installs and opens people.trendlix.com/app (a placeholder page is fine).

### Phase 1 — The phone pages (`/app`)
- Layout: top bar (name, bell), bottom tabs **Home · Requests · Attendance · Payslips · To approve** (the last only for
  managers/leads and those who decide).
- **Home:** today's status, the big **Check in / Check out** button (existing punch endpoint), hours so far, shortcuts
  (Leave · Permission · Reimbursement · Correction), balances (annual leave, permission hours left), upcoming leave and
  holidays.
- **Requests:** my requests of every kind with status and steps; New leave / permission / reimbursement (receipt from
  the camera or gallery) / correction / raise request — the existing forms' rules, phone layouts, native date pickers.
- **Attendance:** the month's days and figures (My Attendance data), a day → Ask for a correction.
- **Payslips:** the list, each opening the protected PDF.
- **To approve:** what waits for the caller (leave, permissions, claims, corrections, raise requests as the CEO/HR may
  see them), approve / reject with a comment.
- Works in a phone browser too. C-level rules and every permission check come from the API as today.
- Done when: an employee and a manager can do all of it from a phone's browser and from the APK.

#### Phase 1 contract — what was built (20 October 2026)

The phone pages live in `apps/web/src/app/(phone)/app/` (their own layout, not the sidebar's). Their addresses are in
`apps/web/src/lib/surface.ts` (`APP_PATHS`, `appItemHref`, …): later phases link to these, never to the site's pages.

| Route | What it is |
|---|---|
| `/app` | **Home**: today's check-in (the site's panel, larger, with the time since checking in), what waits for the caller (deciders), New request tiles (Leave · Permission · Reimbursement · Correction, each only where it applies), balances (annual leave, this month's permission hours), coming up (their leave and permission, the official holidays). |
| `/app/requests` | **Requests**: every request of theirs (leave, permission, reimbursement, correction, raise), newest first, status and where it stands; `?kind=leave\|permission\|reimbursement\|correction\|raise`, `?status=open`; `?sent=1` after a raise request. |
| `/app/requests/new` | New request: the kinds they may ask for now. |
| `/app/requests/new/leave` · `/permission` · `/reimbursement` · `/correction?date=YYYY-MM-DD` · `/raise?employee=<id>` | The site's own forms (shared components), in the phone layout; reimbursement receipts and leave documents add **Take a photo** (`accept="image/*,application/pdf"`, `capture="environment"`) beside the file box. |
| `/app/requests/{leave,permission,reimbursement,correction,raise}/<id>` | A request of theirs: every step, Cancel while it may be; `?done=` says what was just done. |
| `/app/attendance?month=YYYY-MM` | **Attendance**: the month's figures and days (My Attendance's data), each day → Ask for a correction (or the correction being decided). |
| `/app/payslips` | **Payslips**: their months paid (`GET /api/me/payslips`, added for the app), net, month on hold said. |
| `/app/payslips/<lineId>?language=ar` | A payslip drawn in the page with pdf.js (a web view can't show a PDF in a frame), Download PDF, In Arabic/English. |
| `/app/payslips/<lineId>/<en\|ar>?download=1` | The protected PDF (route handler → `GET /api/me/payslips/:lineId/:language`, the caller's own line only, 404 otherwise). |
| `/app/approve` | **To Approve** (managers, team leads, department heads, HR, the CEO, Finance): leave and permission, claims, corrections, raise requests at HR's step, raises with the CEO; endings and details changes linked to the site's Approvals. `?done=raise-…` after the CEO's decision. |
| `/app/approve/{leave,permission,reimbursement,correction}/<id>` | The item with the site's decision form (Approve / Reject + comment; a claim's lower amount too) and every step. |
| `/app/approve/raise/<requestId>` · `/app/approve/pay-raise/<contractId>` | HR's step on a raise request (the CEO's for a C-level person); the CEO's decision on a raise. |

- **One set of forms and actions:** the section's layout says where a form is shown (`components/surface.tsx`, a hidden
  `surface` field = `requests` or `approve`); the site's server actions send it on with `afterAction()` (lib/surface.ts)
  to the same request's page under that section. The page bodies are shared files next to the site's pages
  (`new-leave.tsx`, `leave-request.tsx`, `claim-detail.tsx`, …), each taking `surface`.
- **The native bridge:** `apps/web/src/lib/native.ts` — `isNativeApp()`, `nativePlatform()`, `pluginOf()`,
  `geolocationSource()` / `getPosition()` (the Capacitor Geolocation plugin when the shell carries it, else the
  browser's; the check-in panel reads through it), and stubs for Phase 2–4: `takePhoto()`, `canUseBiometrics()`,
  `verifyBiometrics()`, `registerForPush()`. No Capacitor npm package in the web app.
- **Signed out:** the proxy sends `/app…` to `/login?next=/app…` and back after signing in, as for every page.
- **On the site:** at phone width, "Open the app view" in the header links to `/app`; the app's menu has "Open the
  full site", Change password and Sign out; the bell is a placeholder until Phase 4.
- **Light only**, as the site (`color-scheme: only light`, so a phone's dark mode doesn't darken it); `viewport-fit=
  cover` with the safe-area insets; one column (max 36rem) from 320 px, the tab bar lower in landscape.
- **Open for later phases:** documents and receipts in the request pages still open in the site's document viewer
  (a PDF in a frame: fine in a phone's browser, blank in an Android web view — Phase 2/5 can draw them with pdf.js as
  the payslip is, or open them natively); in the APK, a location permission prompt needs the shell's manifest entries
  (Phase 2).

### Phase 2 — Native location and the camera
- `lib/native.ts`: location through the Capacitor Geolocation plugin inside the app (high accuracy, a timeout, a clear
  message when refused), browser geolocation outside; Android **mock location** → `mock: true` on the punch → flagged
  ("Fake GPS suspected") on Daily Attendance (API + shared rule + label).
- Receipts: the Camera plugin inside the app (photo → upload as today), file input outside.
- Permission texts (Android manifest; later iOS Info.plist): location only while using the app, camera.
- Done when: check-in in the APK uses native location, a fake-GPS app is flagged, a receipt photo uploads.

### Phase 3 — Face ID / fingerprint sign-in
- API: `device_credentials` (user, device name, platform, secret hash, created, last used, revoked) — create (signed-in
  user), exchange (credential → new session, rate-limited, audited), list mine, revoke (mine; HR/Admin any user's);
  sessions made this way are ordinary sessions.
- Web: after a password sign-in inside the app, "Use Face ID / fingerprint next time?"; the app-start screen tries the
  biometric unlock first; profile → **Devices** with Sign out.
- Shell: a biometric plugin + secure storage plugin (Keychain/Keystore), no secret ever in plain storage.
- Done when: second open of the APK signs in with the fingerprint; revoking the device forces the password.

### Phase 4 — Notifications
- API: `push_devices` (user, platform, token, last seen), `notifications` (user, kind, title, body, link, read, created),
  an emitter called from the existing flows (leave/permission/claim/correction/raise request decided or waiting, a
  payslip issued), the FCM sender (off until configured; logs instead), and two reminders run by a scheduler on the API
  server: **"You haven't checked in"** after the shift's latest start + grace on a working day (not on leave/holiday),
  **"Still checked in?"** after the window's end + grace.
- Web: the bell + inbox page, notification settings (which reminders), push registration inside the app.
- Shell: the Push Notifications plugin, the Firebase config file (`google-services.json`, from the owner's Firebase
  project — kept out of the repo, injected in CI from a secret).
- Done when: with push configured, an approval reaches the phone; without it, the inbox shows it.

### Phase 5 — Polish and offline
- The offline screen, pull-to-refresh, app icon and splash from the logo, deep links from notifications to the page,
  back-button behaviour on Android, loading states, accessibility (sizes, contrast, screen readers).
- Optional (if the owner chooses): Arabic interface (RTL).

### Phase 6 — iPhone (after the owner has an Apple Developer account)
- `npx cap add ios`, Info.plist texts (location when in use, Face ID, camera), APNs key in Firebase,
  `.github/workflows/mobile-ios.yml` on macOS runners: simulator build as an artifact without an account; with the
  account, a signed build to TestFlight (signing certificates and profiles in GitHub Secrets).

### Later — the stores
- Release signing, store listings, screenshots, the privacy policy page (location use explained), Apple's guideline
  4.2 (an app that is "just a website" can be refused — the native features are why the app is more than that).

## 4. Rules for the work

- Same conventions as the system (see the repo README and the memories): Title Case headings, sentence case labels and
  buttons, the searchable Select, DD/MM/YYYY, 12-hour times, comments with the owner's words and dates.
- No personal data in the repo, the app or the CI logs; no secrets in the repo (Firebase key, keystores → GitHub
  Secrets / deploy/.env, never in chat).
- The API stays private: the app reaches only `people.trendlix.com`.
- The phone pages reuse the existing loaders, actions and shared rules — no second copy of a rule.
- Parallel agents split by area (API / web pages / shell); agree a contract first (endpoints and shapes) and write it
  here under the phase.
- Before each push: every check green; then watch the web deploy, the backend deploy and the mobile workflow.

## 6. Installing a test APK (for the owner)

1. GitHub → the repository → **Actions** → **Mobile (Android)** → the newest green run.
2. At the bottom, **Artifacts** → **trendlix-people-…** (e.g. `trendlix-people-0.1.7`) → download (a .zip) → open it
   to get the `.apk`. A build from a `mobile-v…` tag is also on the repository's **Releases** page as a plain `.apk`.
3. Send it to the Android phone (or download it on the phone), tap it, allow "Install unknown apps" the first time,
   **Install**. A newer APK installs over the old one. If the phone ever says the app can't be installed because it
   conflicts with the one already there, the build's signing key changed (see section 7, the signing key): uninstall
   TrendLIX People once, then install the new one.

## 7. Building Locally

What is in `apps/mobile` (the npm workspace `@trendlix/mobile`, installed from the repo root with the rest):

- `capacitor.config.ts` — app id, name, `server.url` (`https://people.trendlix.com/app`), `allowNavigation`, the offline
  page (`server.errorPath`), Android WebView settings. `www/index.html` is a tiny loader (never shown while `server.url`
  is set); `www/offline.html` is the no-connection page with Retry.
- `android/` — generated by `npx cap add android` (Capacitor 8.5.3) and committed. The only hand edit so far: the
  version lines in `android/app/build.gradle` (`MOBILE_VERSION_CODE` / `MOBILE_VERSION_NAME`, default 1 / `0.1.0`).
  `npx cap sync android` recreates what is not kept in git: `app/src/main/assets/public` (a copy of `www`),
  `assets/capacitor.config.json`, `assets/capacitor.plugins.json`, `res/xml/config.xml`,
  `capacitor-cordova-android-plugins/`.

```sh
npm install                                    # repo root; the workspace's Capacitor and TypeScript come with it
npm run typecheck -w @trendlix/mobile          # tsc on capacitor.config.ts
npm run sync -w @trendlix/mobile               # = npx cap sync android; after any change to the config or www
npm run doctor -w @trendlix/mobile             # = npx cap doctor
cd apps/mobile/android && ./gradlew assembleDebug   # needs JDK 21 and the Android SDK (Android Studio installs both)
#   → apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk
npm run open:android -w @trendlix/mobile       # opens the project in Android Studio (run it on a phone or emulator)
```

- To try a local web server in the app, change `server.url` to `http://<the computer's LAN address>:3000/app` with
  `cleartext: true`, sync, build — and never commit that.
- A computer's build has version code 1 and its own debug key, so it doesn't install over a CI build (or the other way
  round) without uninstalling first.
- **The signing key of the CI builds.** A phone only updates an app with an APK signed by the same key. CI keeps the
  debug key Gradle makes on its first run in the Actions cache (`android-debug-keystore-v1`); GitHub drops a cache not
  used for 7 days, and the next build then has a new key (uninstall once). To keep one key for good, save a debug
  keystore as the repository secret `ANDROID_DEBUG_KEYSTORE_BASE64` (on a computer with a JDK; the file is a test key
  for debug builds only, never the store key):

  ```sh
  keytool -genkeypair -keystore debug.keystore -storepass android -keypass android -alias androiddebugkey \
    -keyalg RSA -keysize 2048 -validity 10000 -dname "CN=Android Debug,O=Android,C=US"
  base64 -i debug.keystore | gh secret set ANDROID_DEBUG_KEYSTORE_BASE64 && rm debug.keystore
  ```

  The run's summary shows the signing certificate's SHA-256: the same value from build to build means the APK updates
  in place.
- **For the phone pages (Phase 1):** inside the app `window.Capacitor` is injected on `https://people.trendlix.com`
  pages only, and the user agent ends with `TrendLIXPeople`. The offline page is shown not only without a connection
  but also when the page itself answers with an HTTP error (4xx/5xx), so `/app` must answer 200 or redirect (today it
  redirects to `/login?next=%2Fapp`). Links to any other site open in the phone's browser.
