# Trendlix People — the employee mobile app: plan and development guide

This file is the working guide for building the employee app. Read it before every session of work on the app, keep
the **Status** section at the bottom up to date at the end of each phase, and record every decision the owner makes
here (with the date and their words) before building on it.

---

## 1. What the owner asked for (20 October 2026)

- "what if we tried to build a mobile app for the employees? to enable them to check in and out, and apply for their
  requests" — then, from Claude's options:
  - **A store app** (App Store and Google Play, later) wrapping the web system — not a separate native rebuild.
  - **First version:** Check in / Check out · Requests (leave, permission, reimbursement with a receipt photo,
    attendance corrections, raise requests) · My attendance and payslips · managers and team leads approve from the
    phone.
  - **Push notifications:** yes (decisions, things waiting for someone, a check-in reminder).
  - **Sign-in:** Face ID / fingerprint after the first password sign-in.
- "we will not test the first version of the app on google play or on app store but we will deploy apps on github and
  use github action with yml ci cd file; actions will be responsible for build the app so that i can download the apk
  app to test it while developing process phases."
  - So: **no store submission in the first version.** Every phase ends with an **APK built by GitHub Actions** that
    the owner downloads from the workflow run (or a GitHub Release) and installs on an Android phone.
  - iPhone: an unsigned build can't be installed on a phone without an Apple Developer account, so iOS comes after the

  (2–3 days, RTL) and not decided yet — build every string so it can be translated later (no text in native code).

## 2. The shape of it (architecture)

```
 Android / iOS phone
 ┌───────────────────────────────────────────────┐
 │  Trendlix People (Capacitor shell, apps/mobile) │
 │  ├─ WebView → https://people.trendlix.com/app   │  the phone pages (apps/web, Next.js, /app routes)
 │  └─ native plugins: location, push, biometrics, │  reached from the pages through window.Capacitor
 │     camera, secure storage, network status      │
 └───────────────────────────────────────────────┘
                  │ HTTPS (the website only)
                  ▼
   Vercel: apps/web (Next.js) ── server-side ──► API (NestJS, VPS, private CA) ──► PostgreSQL
```

- **Why the app loads the website's pages:** the system's pages are server-rendered (server components, server
  actions) and the API is reachable **only from the website** (private CA — see DEPLOY.md and the job-offers memory).
  So the app never calls the API directly: it shows `people.trendlix.com/app/...`, and the website talks to the API as
  it does today. Every rule (approvals, C-level hiding, limits, grace, payroll filling) stays in one place.
- **The phone pages (`/app`)** are a separate, phone-first area of the web app with its own layout (bottom tab bar, big
  touch targets, one hand), reusing the existing data loaders, server actions and shared rules. They also work in a
  phone's browser, so each phase can be tried before the APK exists.
- **The native bridge:** pages call native features only through one helper, `apps/web/src/lib/native.ts`, which
  feature-detects `window.Capacitor` (present only inside the app) and falls back to the browser's own APIs
  (navigator.geolocation, file input with `capture`) when it isn't. The web app does **not** depend on Capacitor npm
  packages; it uses the injected `window.Capacitor.Plugins` with typed wrappers.
- **The shell (`apps/mobile`):** a Capacitor project (`capacitor.config.ts` with `server.url` =
  `https://people.trendlix.com/app`, `allowNavigation` for the domain), the Android project (`android/`), later the iOS
  project (`ios/`), plugins, app icon and splash from the company logo, permission texts, and an offline screen bundled
  in `www/` (shown when the site can't be reached).
- **Signing in on the phone:**
  1. The first time: the normal sign-in page (work email + password) inside the app → a normal web session cookie.
  2. The app then offers "Use Face ID / fingerprint next time": the website asks the API for a **device credential**
     (a random secret, stored hashed in the database per user and device, long-lived, revocable); the app keeps it in
     the phone's secure storage (Keychain / Android Keystore) behind the biometric prompt.
  3. Next opens: biometric prompt → the app sends the device credential to the website → the website asks the API for a
     fresh session and sets the cookie → the app opens Home. A revoked or expired credential falls back to the password.
  4. The user's devices are listed on their profile (and for HR/Admin) with "Sign out this device" (revoke).
- **Push notifications:** Firebase Cloud Messaging (FCM, HTTP v1) for Android now (and iOS through APNs later). The app
  registers its push token with the website → API (`push_devices`). The API sends through a small FCM client written
  with Node's own crypto + fetch (no new dependency), **switched off until the owner creates the Firebase project** and
  the service-account key is set on the server (`FCM_PROJECT_ID`, `FCM_CLIENT_EMAIL`, `FCM_PRIVATE_KEY` in
  deploy/.env — never asked for in chat). An in-app **inbox** (bell) holds the same notifications, so nothing is lost
  while push is off.
- **Location:** check-in already classifies office / remote / unknown on the server from the coordinates sent and keeps
  no coordinates (see packages/shared check-in.ts). In the app, the native location plugin gives better accuracy, and on
  Android it reports **mock (fake GPS) locations** — sent as `mock: true` and flagged on the day like a check-in from
  the wrong place.

## 3. Phases (each ends with a downloadable APK and a short note to the owner)

Every phase: build → all checks (API unit, the whole e2e suite, tsc, lint; web typegen, tsc, eslint, vitest, build;
the mobile workflow green) → commit and push to main (auto-push rule) → the web deploy (Vercel) and backend deploy
(GitHub Actions) as today → the **Android APK** from the mobile workflow → tell the owner where to download it and what
to try.

### Phase 0 — Scaffolding and CI (the APK pipeline)
- `apps/mobile`: package.json (`@trendlix/mobile`), Capacitor core + CLI + Android platform, `capacitor.config.ts`,
  `www/` with the offline page and a tiny loader, `android/` generated by `npx cap add android` and committed.
- App id `com.trendlix.people`, name **Trendlix People** (renamed by the owner in Phase 5, 20 October 2026: "App Name:
  Trendlix People"), version from the workflow run number.
- `.github/workflows/mobile-android.yml`:
  - on: push to main touching `apps/mobile/**` (and the workflow file), plus `workflow_dispatch` (run by hand), plus
    tags `mobile-v*` (also attaches the APK to a GitHub Release).
  - ubuntu-latest, Node 22 (the repo's engines), Java 21 (Temurin), Android SDK via the runner's preinstalled SDK.
  - `npm ci` → `npx cap sync android` → `./gradlew assembleDebug` (Phase 0–5: debug-signed APK, installable directly)
    → upload `app-debug.apk`, renamed `trendlix-people-<version>.apk`, as an artifact named
    `trendlix-people-<version>`, kept 30 days.
  - Later (before any store): a release build signed with a keystore kept in GitHub Secrets.
- How the owner installs it: Actions → the latest "Mobile (Android)" run → Artifacts → download → unzip → open the APK
  on the phone (allow "install unknown apps" once). The README's section 6 says this in plain words.
- Done when: a push builds an APK that installs and opens people.trendlix.com/app (a placeholder page is fine).

#### Phase 2 — what was built (20 October 2026)

- **The plugins** (in `apps/mobile/package.json`, exact versions, the lock file updated, `npx cap sync android` run and
  its two generated Gradle files committed: `android/capacitor.settings.gradle`, `android/app/capacitor.build.gradle`):
  `@capacitor/geolocation` **8.2.4** and `@capacitor/camera` **8.2.6** (both for Capacitor 8, written in Kotlin; the
  plugin modules bring their own Kotlin Gradle plugin, so the app's Gradle files need nothing for it).
- **Fake GPS — the app's own plugin `TrendlixLocation`** (`android/app/src/main/java/com/trendlix/people/
  TrendlixLocationPlugin.java`, registered in `MainActivity.java` before the bridge starts). The Geolocation plugin
  does **not** say whether a location is a mock one (its Android code drops it), so this small Java plugin reads the
  location itself and adds Android's own word on it:
  - `getPosition({ enableHighAccuracy, timeout, maximumAge })` → `{ latitude, longitude, accuracy, timestamp, mock }`.
  - It asks for the location permission with the system's prompt (precise, or approximate only, both read), checks
    the phone's location is on, then asks Google Play services' **fused location** once (as the Geolocation plugin
    does: high accuracy, within the timeout, no older reading than `maximumAge`).
  - `mock` is `Location.isMock()` on Android 12 and later, `Location.isFromMockProvider()` before: true when the
    location came from a **mock location app** (Developer options → *Select mock location app*, which every fake-GPS
    app needs). Nothing else is guessed (no list of apps, no root check).
  - Refusals are codes, never text for people (the pages word them): `DENIED`, `LOCATION_OFF`, `TIMEOUT`,
    `UNAVAILABLE`, and `NO_PLAY_SERVICES` (a phone without Google Play services: the page then asks the Geolocation
    plugin, whose own fallback uses Android's location manager — **mock not known** there).
  - One new Gradle line for it: `com.google.android.gms:play-services-location` in `app/build.gradle`, at
    `playServicesLocationVersion = '21.3.0'` in `variables.gradle` (the version the Geolocation plugin uses too).
- **The manifest** (`android/app/src/main/AndroidManifest.xml`): `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION`,
  `CAMERA`; `ACCESS_BACKGROUND_LOCATION` removed with `tools:node="remove"` (never in the background, whatever a library
  asks for); GPS and camera hardware `required="false"`. Android's permission prompts carry no text of the app's (the
  page says why it asks: "Each press asks your phone for your location …"); iOS's Info.plist texts come in Phase 6.
- **The web bridge** (`apps/web/src/lib/native.ts`): `getPosition()` asks `TrendlixLocation` first inside the app (high
  accuracy, 10 s, `maximumAge: 0`, the 30 s give-up of the check-in), then the Geolocation plugin, then the browser's
  `navigator.geolocation`; the point carries `mock` only when the app's plugin said it (a browser: left out, "not
  known"). `takePhoto()` opens the Camera plugin's `takePhoto` (the back camera, upright, not saved to the gallery) and
  reads the photo from the address the shell serves it at (`webPath`, on the site's own origin), as a `File`
  (`photo-YYYYMMDD-HHMMSS.jpg`); closing the camera says nothing, a refused camera says how to allow it.
  `canTakePhoto()`, `lib/use-native.ts` (`useNativeApp()`, false while hydrating).
- **The pages:** the check-in panel says, after a press whose location couldn't be read, what to do (inside the app:
  Settings → Apps → Trendlix People → Permissions → Location → Allow only while using the app); **Take a photo** on
  receipts and leave documents (`components/camera-button.tsx`) opens the app's camera inside the app and the file box
  with `capture` outside; the **document viewer** draws a PDF with pdf.js (`components/pdf-view.tsx`) on the `/app`
  pages and anywhere inside the app (no frame, no "Open in a new tab" in the app); pictures as before.
- **The API and the shared rule:** `POST /me/attendance/punches` takes `mock: boolean` (optional; anything else is
  refused). A press with `mock: true` is kept like any other (its place read from the point; the point itself kept with
  the press since 20 October 2026, "Yes, keep the spot", seen by HR, the CEO, the Super Admin and the employee) and
  flagged **`fake_gps` — "Fake GPS suspected"** (packages/shared `check-in.ts`: `CHECK_IN_FLAGS`, `punchFlags`), on a
  check-in whatever the arrangement and on a check-out too (a check-out's place breaks no rule, but a made-up location
  is suspected all the same); the day takes it (`dayFromPunches`), so Daily Attendance shows it, counts it in Flagged
  days, lists it under **Only with flagged check-ins**, and the Excel export words it. Migration
  `20261020060000_fake_gps_flag` widens the two flag checks. Not in the audit log (the punches are their own record).
  The web's server action sends a press again without `mock` if an API from before it refuses the word (the web and
  the API are deployed apart).
- **What only CI and a phone can prove** (no JDK or Android SDK on the Mac): the Gradle build with the two Kotlin
  plugins and the Java plugin; then on a phone: the location prompt on the first Check in, check-in from the office and
  away, "Allow only while using the app" offered and no background location; a fake-GPS app (set as the mock location
  app in Developer options) giving "Fake GPS suspected" on the punch and on Daily Attendance; Take a photo opening the
  camera and the receipt uploading; a PDF receipt or leave document drawn in the viewer.

### Phase 3 — Face ID / fingerprint sign-in
- API: `device_credentials` (user, device name, platform, secret hash, created, last used, revoked) — create (signed-in
  user), exchange (credential → new session, rate-limited, audited), list mine, revoke (mine; HR/Admin any user's);
  sessions made this way are ordinary sessions.
- Web: after a password sign-in inside the app, "Use Face ID / fingerprint next time?"; the app-start screen tries the
  biometric unlock first; profile → **Devices** with Sign out.
- Shell: a biometric plugin + secure storage plugin (Keychain/Keystore), no secret ever in plain storage.
- Done when: second open of the APK signs in with the fingerprint; revoking the device forces the password.

#### Phase 3 contract — what was built (20 October 2026)

The owner chose Face ID / fingerprint sign-in for the app (20 October 2026). On Android it is the **fingerprint**: only
a *strong* (Class 3) biometric can unlock a Keystore key, and many Android face unlocks are *weak* (Class 2), so on those
phones the prompt takes the fingerprint only (a phone whose face unlock is Class 3, e.g. a Pixel 8 or later, may offer
the face too). The shared rules: `packages/shared/src/device-credentials.ts`.

**The API** (`apps/api/src/auth/`: `device-credentials.service.ts`, `device-rules.ts`, `user-devices.controller.ts`;
table `device_credentials`, migration `20261020110000_device_credentials`):

| Endpoint | Who | Body → answer |
|---|---|---|
| `POST /auth/devices` | the signed-in user, on an **app** session only, never while viewing as someone | `{ deviceName, platform: 'android' \| 'ios' }` → 201 `{ id, secret }`, the secret this once (32 random bytes, base64url). The user's active credential with the same device name and platform is revoked (`replaced`). 403 on a website session or while viewing as someone. |
| `POST /auth/devices/sign-in` | public, like login | `{ id, secret, userAgent?, ip? }` → 200 `{ id, email, roles }` and the session cookie, like login: an ordinary **app** session (it replaces the user's older app session; the 15 minutes apply). 401 `{ message: 'Sign in with your password this time.', reason: 'unknown' \| 'revoked' \| 'expired' }`; 429 after 10 refusals of a credential, or 20 from one address, within 15 minutes. |
| `GET /auth/devices` | the signed-in user (the one viewed as, while viewing) | → `[{ id, deviceName, platform, createdAt, lastUsedAt }]`, newest first: the ones that still sign in. |
| `POST /auth/devices/:id/revoke` | the signed-in user, their own | → 204 (`signed_out`); another's: 404. |
| `GET /users/:userId/devices` | Admin, Super Admin | → the same list for that user. |
| `POST /users/:userId/devices/revoke` · `POST /users/:userId/devices/:id/revoke` | Admin, Super Admin; a Super Admin's only a Super Admin | → 200 `{ revoked: n }` (`revoked`). |

- The table keeps the secret's SHA-256 only (`secret_hash`), compared in constant time; never the secret, nor in the
  audit log. A credential signs in when it isn't revoked, its account is active, and it was used (or made) within the
  last **90 days**; one past the 90 days is revoked (`expired`) when tried.
- Revoked by themselves: deactivating the account (`deactivated`), a password change (`password_changed`: the user's
  **other sessions end too**, on the website and the app), a reset by an Admin (`password_reset`).
- Audit: `device_add` "Turned on fingerprint sign-in", `device_login` "Signed in with fingerprint" (also the Users
  page's last sign-in), `device_login_failed` "Fingerprint sign-in refused" (the reason and the address, never the
  secret), `device_revoke` "Turned off fingerprint sign-in".

**The shell's plugin `TrendlixBiometric`** (`android/app/src/main/java/com/trendlix/people/TrendlixBiometricPlugin.java`,
registered in `MainActivity.java`; AndroidX Biometric `androidx.biometric:biometric` **1.1.0**, the current stable, at
`androidxBiometricVersion` in `variables.gradle`). An AES-256-GCM key in the Android Keystore that needs a strong
biometric for every use (`setUserAuthenticationRequired(true)`, `setInvalidatedByBiometricEnrollment(true)`); the
secret is encrypted with it behind the prompt, and only the ciphertext, its IV and the credential's id are kept, in the
app's private preferences. The secret is never logged.

| Method | Answer |
|---|---|
| `isAvailable()` | `{ available, reason?: 'NONE_ENROLLED' \| 'NO_HARDWARE' \| 'WEAK_ONLY' \| 'UNAVAILABLE', deviceName }` (`deviceName`: e.g. "Google Pixel 8"). |
| `isEnrolled()` | `{ enrolled, id? }`: a secret is kept (and its key is still there). |
| `enroll({ id, secret, title?, negativeButtonText? })` | the prompt (ENCRYPT) → `{ enrolled: true }`. |
| `unlock({ title?, negativeButtonText? })` | the prompt (DECRYPT) → `{ id, secret }`. |
| `clear()` | the key and what is kept are deleted → `{}`. |

- Refusals are codes only: `CANCELLED` (closed, or "Use password"), `LOCKOUT` (too many tries), `KEY_INVALIDATED` (a
  fingerprint was added or removed since: everything is cleared and the password is asked for), `NOT_AVAILABLE` (no
  strong biometric enrolled, or nothing kept), `FAILED`.
- The prompt's texts come from the page (no text for people in native code), with English defaults: "Sign in to Trendlix
  People" and "Use password".
- One prompt at a time (a second call while one is open: `FAILED`); a prompt with no answer within 2 minutes is given up
  as `CANCELLED`.
- `capacitor.config.ts` sets `loggingBehavior: 'none'`: Capacitor's bridge would otherwise write every plugin call's
  options and answer (the secret among them) to logcat in the debug APKs CI builds.

**The website** (`apps/web`):
- `lib/native.ts`: `biometricStatus()`, `enrollBiometric(id, secret)`, `unlockBiometric()`, `clearBiometric()` through
  `pluginOf('TrendlixBiometric')`; outside the app all unavailable.
- **Home (`/app`)**, inside the app, signed in with the password: "Use your fingerprint to sign in next time?" with
  **Turn on** (a server action makes the credential, the page hands the secret to the plugin: never to localStorage)
  and **Not now** (remembered on the phone). Not shown when the phone can't, it is already on, or while viewing as
  someone.
- **The sign-in page**, inside the app with a fingerprint kept: **Sign in with fingerprint**, asked once by itself when
  the page opens, unless the person has just signed out (`?reason=signed_out`). Then a server action trades `{ id,
  secret }` for the session cookie and opens `next` or `/app`. A 401 clears the phone's credential ("Sign in with your
  password this time."); a changed fingerprint too ("Your fingerprints changed: sign in with your password.").
- **Signing out in the app** keeps the fingerprint (the next open offers it) and lands on `/login?reason=signed_out`,
  which doesn't ask for it by itself.
- **Your Sessions**: "Fingerprint Sign-In", the person's phones (name, platform, added, last used) with Sign out; this
  phone's clears the app's copy too. **Users page**: the person's phones beside their sessions, Sign out and Sign out all
  devices (Admin, Super Admin).

### Phase 4 — Notifications
- API: `push_devices` (user, platform, token, last seen), `notifications` (user, kind, title, body, link, read, created),

**The reminders** (`reminder-rules.ts`, pure, tested with a fake clock; `reminders.service.ts`): `main.ts` starts a timer
every minute in the API process (the tests' apps don't start it; they call `runOnce(now)`). A round first reads the
shifts and goes on only with the people of those within their reminders' hours now (`liveShiftIds`: the 2 hours from a
start, or the 4 hours after hours stop counting), so most rounds stop there. Each round runs in a
transaction holding a Postgres advisory lock (`pg_try_advisory_xact_lock(hashtext('people-system notification
reminders'))`): another process finding it held sends nothing that round. Cairo time; the day before today is looked at
too (a night shift's day is the day it starts).
- **"You haven't checked in"** / "Your shift started at 9:00 AM. Check in now." (owner, 20 October 2026: "a reminder

  stopping "After 2 hours", "No, always on"): on a working day of the person's shift (not on approved leave, an official
  holiday, a day off of the shift, or with approved permission covering the shift's start; a permission without times
  counts as covering it), not checked in: at the shift's start (9:00 AM for MORNING, not after the grace), then every 10
  minutes, the last no later than 2 hours on: 9:00, 9:10 … 10:50, **12 at most** (none once the day's hours stop
  counting). It stops as soon as they check in. **Always on**: the person's switch is ignored. Each 10-minute step goes
  once whichever process sends it: the step is claimed on the `reminders_sent` row in the round's transaction (`INSERT …
  ON CONFLICT DO UPDATE SET count = count + 1 … WHERE last_sent_at < the step's start AND count < 12`); a round late

refused access token is asked for again once; every call has a 10-second limit; nothing is thrown into a flow; never a

## 7. Building Locally

What is in `apps/mobile` (the npm workspace `@trendlix/mobile`, installed from the repo root with the rest):

  splash icon and the pages' wordmark from them (Phase 5; how to run it and what it writes: `assets/README.md`).
- `android/` — generated by `npx cap add android` (Capacitor 8.5.3) and committed. The hand edits: the version lines
  in `android/app/build.gradle` (`MOBILE_VERSION_CODE` / `MOBILE_VERSION_NAME`, default 1 / `0.1.0`); Phase 2's
  permissions in `AndroidManifest.xml`, the app's own plugin `TrendlixLocationPlugin.java` registered in
  `MainActivity.java`, and Google Play services' location in `app/build.gradle` and `variables.gradle`; Phase 3's own
  plugin `TrendlixBiometricPlugin.java` (registered there too) and AndroidX Biometric in the same two Gradle files (the
  manifest is unchanged: the library brings `USE_BIOMETRIC`); Phase 4's own plugin `TrendlixPushPlugin.java` (registered
  there too), and in the manifest `POST_NOTIFICATIONS` and Firebase's default channel and icon; Phase 5's resources
  (`assets/README.md`: the icons' and splash's PNGs and XML, `values/colors.xml`, the launch theme's splash items, the
  manifest's notification icon and colour), the old splash PNGs and the template's unused icon vectors removed.
  `app/google-services.json`
  is written by CI from the secret `GOOGLE_SERVICES_JSON` and never committed; a build on a computer without it has no
  push (to try push locally, download it from Firebase into `android/app/`, and never commit it). After adding a
  plugin package, `npx cap sync android` rewrites `capacitor.settings.gradle` and `app/capacitor.build.gradle` (kept
  in git, never edited by hand).
  `npx cap sync android` recreates what is not kept in git: `app/src/main/assets/public` (a copy of `www`),
  `assets/capacitor.config.json`, `assets/capacitor.plugins.json`, `res/xml/config.xml`,
  `capacitor-cordova-android-plugins/`.

```sh
npm install                                    # repo root; the workspace's Capacitor and TypeScript come with it
npm run typecheck -w @trendlix/mobile          # tsc on capacitor.config.ts
npm run sync -w @trendlix/mobile               # = npx cap sync android; after any change to the config or www
npm run doctor -w @trendlix/mobile             # = npx cap doctor
npm run assets -w @trendlix/mobile             # = node assets/generate.mjs; after changing a logo (assets/README.md)
cd apps/mobile/android && ./gradlew assembleDebug   # needs JDK 21 and the Android SDK (Android Studio installs both)
#   → apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk
npm run open:android -w @trendlix/mobile       # opens the project in Android Studio (run it on a phone or emulator)
```

- To try a local web server in the app, change `server.url` to `http://<the computer's LAN address>:3000/app` with
  `cleartext: true`, sync, build — and never commit that.
- A computer's build has version code 1 and its own debug key, so it doesn't install over a CI build (or the other way
  round) without uninstalling first.
- **The signing key of the CI builds.** A phone only updates an app with an APK signed by the same key. CI keeps the
  debug key Gradle makes on its first run in the Actions cache (`android-debug-keystore-v1`); GitHub drops a cache not
  used for 7 days, and the next build then has a new key (uninstall once). To keep one key for good, save a debug
  keystore as the repository secret `ANDROID_DEBUG_KEYSTORE_BASE64` (on a computer with a JDK; the file is a test key
  for debug builds only, never the store key):

  ```sh
  keytool -genkeypair -keystore debug.keystore -storepass android -keypass android -alias androiddebugkey \
    -keyalg RSA -keysize 2048 -validity 10000 -dname "CN=Android Debug,O=Android,C=US"
  base64 -i debug.keystore | gh secret set ANDROID_DEBUG_KEYSTORE_BASE64 && rm debug.keystore
  ```

  The run's summary shows the signing certificate's SHA-256: the same value from build to build means the APK updates
  in place.
- **For the phone pages (Phase 1):** inside the app `window.Capacitor` is injected on `https://people.trendlix.com`
  pages only, and the user agent ends with `TrendLIXPeople` (kept when the app was renamed in Phase 5: the server tells
  app sessions by it, and installed APKs send it). The offline page is shown not only without a connection
  but also when the page itself answers with an HTTP error (4xx/5xx), so `/app` must answer 200 or redirect (today it
  redirects to `/login?next=%2Fapp`). Links to any other site open in the phone's browser.
